## 这一轮要回答什么

先验证：一个第一次使用的人，能否把熟悉的一餐记下来，在地图里找回它，并愿意再记第二条。记录时的困难和回看时的价值分开观察，避免只问“好不好用”。

建议 8–12 位 Windows 电脑使用者，每人约 10 分钟，分两批推进。人数和时长都是计划，不是执行结果。首批先看启动与第一条记录，修正明显卡点后再开展下一批；两批若版本不同，分别统计。

中国地图 v0.7.0 已公开提供，包含五家特色店灵感与无需 Token 收藏、多词搜索、餐品回忆入口、“再来这家”，并保留单篇探店卡、复制图片、足迹分享卡、年度回忆、想去清单以及页面连接官方 MCP 与同步订单。正式体验招募仍按用户具体渠道安排；宣传与下载操作说明见 [GROWTH.md](GROWTH.md)。

2026-10-10 本对话已核对 v0.7.0 公开发行及 ZIP 附件 uploaded；主开发报告对应 CI 成功，未重复包测试。下一版“分享下一站”计划卡尚未发包，仅记开发进度，不当作当前可体验功能或外部用户反馈。

## 反馈资料的隐私边界

按用户最新要求，**真实订单关联的门店、地址和图片只留在本机，不上传 GitHub，也不用于宣发**。主持人不从 `private/` 取素材，不收集私人订单截图或图片链接；匿名化、遮挡订单号也不能让这些资料进入公开文档。

此文件位于可公开的仓库文档目录，只记录不含私人细节的操作事实、匿名汇总与问题结论。用户原话若包含实际门店、地址、订单细节或图片信息，不原样写入；改用“门店 A”“城市 A”等占位转述并明确标注。无法在不泄露信息的前提下保留证据，就只记问题类型、发生步骤和待验证结论，不写私有文件名或路径。

公开截图与复现使用人民广场等其他公开门店的虚构记录，先确认不关联用户真实订单。真实私人资料不作为本轮可公开引用或截图的候选。

体验记录可以虚构，但“体验者操作与反馈”必须真实。虚构记录不能作为到访证据，也不能拿来做真实用户故事。

## 体验步骤

主持人先说明是记录体验，不是测试参加者。出现困难时先观察；需要帮助就直接帮助，并记下帮助发生在哪一步，不让对方反复受挫。

| 步骤 | 给体验者的任务 | 观察与记录 |
| --- | --- | --- |
| 1. 打开 | 用提供的 Windows 包打开产品 | 是否知道从哪里启动；遇到的具体提示；所用包版本、浏览器；是否需要协助 |
| 2. 看一眼 | 先看页面，说说你觉得它能用来做什么 | 用体验者原话记录理解，先不解释定位 |
| 3. 记一餐 | 记下自己熟悉的一家门店，也可自编记录；照片与随手记任选 | 是否找到新增入口；省份、城市、门店是否容易填；保存是否成功；用时和协助情况 |
| 4. 找回来 | 回到地图，找到刚才那条记录，再打开看一眼 | 是否理解省份点亮与城市标记；是否期待精确门店位置；能否找回记录 |
| 5. 保存与备份 | 刷新看看记录是否还在，导出一份备份 | 刷新是否保留；是否知道文件用途；备份只留在体验者本机，不发送给主持人 |
| 6. 再记的理由 | 说说下次什么情况下会再次打开它 | 具体场景与顾虑；口头意愿单独记录，不能当成实际回访 |

导入恢复可以在自愿的独立环节进行：使用专门的空白浏览器上下文和体验者自己的体验备份，确认记录能恢复；不要覆盖日常手账。若没有做，只记“未体验”，不要记为通过。

普通体验不要求 MCP。官方门店查询与历史订单确认邀请已具备接入条件且自愿参加的人另测；使用者自己输入 Token，主持人不读取、不收集原始订单及其关联门店、地址或图片。主开发确认 v0.2.0 已包括自动补资料、默认照片和用户上传优先；需要体验这些路径时，使用对应公开版本。

v0.5.0 的 MCP 体验使用新入口：电脑有 Python 3.10+ 时运行「启动.cmd」，在页面点“连接麦当劳”，连接后点“同步我的订单”，核对直接出现的候选卡。记录是否找到入口、有没有看懂候选与本人到店确认；不再让新体验者先另开启动窗口或寻找导入文件。来源为主开发实际验收与公开发行状态，不当作外部体验者完成数据。

v0.6.0 可加一项自愿体验：选一页记录，生成探店卡，选择是否展示城市／门店与照片全图／裁切，再复制或保存图片。询问“卡片有没有保留你最想让朋友看到的内容？”及“照片呈现和城市／门店选项是否容易理解？”。不把复制成功计为已向外部发送，不把主开发本地验收计为外部受众完成。

v0.3.0 可增加一项自愿任务：生成足迹分享卡，打开分享面板，查看可选应用；年度回忆另看能否找回某一餐。记下设备、浏览器、是否出现面板与是否取消；只有体验者确实完成发送才记录发送结果。补问“你想把这张卡发给谁？”与“哪一步让你停住了？”。设备不支持时观察保存图片或复制文案是否容易找到。

v0.7.0 可选三个短任务，不增加每人必做步骤：不连接 Token，从五家特色店中选一家收藏并留理由；用城市／餐品等词找回已有记录；从旧记录点“再来这家”，保存一条新记录。观察是否理解“想去”与“已到访”的区别、搜索词是否符合习惯、新旧记录是否容易区分。页脚反馈入口可让体验者自愿使用，公开 Issue 不填私人订单、Token 或真实订单关联的门店／地址／图片。这些外部体验任务目前未执行，不计为通过或外部反馈。

## 反馈问题

先问实际发生的事，再问期待；可以按过程选问，不强迫每位体验者回答整套问卷。

1. 刚打开时，你觉得这个页面可以用来做什么？
2. 记录这一餐时，哪一步让你停住了？你当时以为应该怎么做？
3. 哪项信息最难填？如果不记这一项，会不会更愿意保存？
4. 回到地图以后，你是怎么找刚才那条记录的？有没有和预期不同的地方？
5. 这条记录让你想起了什么？和直接翻相册或看订单相比，它对你有没有用，为什么？
6. 下次你会在什么时候再打开它？如果不会，最主要的原因是什么？
7. 如果只能改一个地方，你会选哪里？改完会帮助你完成什么？

可选补问：你觉得照片、餐品、随手记中哪项最想留下？你现在在哪里记这些？不要把“自动导入是不是很方便”“喜欢这个地图吗”作为主要问题。

进阶体验分别询问：门店查询是否帮助少填信息；订单候选核对是否容易理解；哪些城市或省份仍需补充。只有亲自体验后才记录这些模块的结果。

## 如何确定优先级

人数不是唯一依据，先看问题是否阻断记录或导致丢失，再看它影响多少实际体验者。

| 优先级 | 判定依据 | 下一步验证 |
| --- | --- | --- |
| P0 | 已有证据显示保存／刷新导致记录丢失，或备份恢复破坏现有记录 | 保留问题版本与复现步骤；使用虚构数据独立复现；验证修复后记录完整，并回访实际受影响者 |
| P1 | 无法启动、无法保存第一条、核心路径必须反复求助 | 定位最早卡住的步骤；验证相同环境下能完成该步骤，再观察首次使用者能否独立完成 |
| P2 | 能完成记录，但找回、理解地图或填写信息有明显负担；有证据支持的新需求 | 明确要减少哪个动作或误解；用针对该路径的体验比较验证，不直接照单增加功能 |
| P3 | 少量外观偏好、使用场景尚不清楚的建议 | 保留原话，确认场景和期望；证据不足先不安排开发 |

P0 仅需可信的单例就应调查；影响人数未知写“未知”。所有建议先写反馈事实，再提出解释与方案；解释是待验证判断，不能伪装成用户要求。

主开发对话可读取此表，将已核实问题转成开发任务。此文档不自行安排发布或向其他对话发送消息。

## 一轮结束后怎么复盘

以下字段目前全部待收集，不填写假设数字：

- 实际邀请、报名、开始体验的人数分别是多少？“已发邀请”不等于“已开始”。
- 开始体验的人中，独立保存第一条、协助后保存、未保存分别多少？附具体版本和最常见卡点。
- 实际体验地图找回、刷新保留、导出与恢复的人数及结果分别是多少？未体验单列。
- 愿意再记录与不愿意的具体理由是什么？后续实际回访另外统计，不用意愿替代。
- 有哪些已核实问题必须先修？有哪些需求证据还不足？是否具备扩大招募的条件？

主持人观察、用户自述、用户转述、产品推断分别标注。每次复盘保留版本与证据编号，下一轮才能判断问题是否真的改善。
