## 这一轮要回答什么

先验证：一个第一次使用的人，能否把熟悉的一餐记下来，在地图里找回它，并愿意再记第二条。记录时的困难和回看时的价值分开观察，避免只问“好不好用”。

建议 8–12 位手机浏览器使用者，每人约 10 分钟，分两批推进。人数和时长都是计划，不是执行结果。首批先看点链接打开与第一条记录，修正明显卡点后再开展下一批；两批若版本不同，分别统计。

当前交付为 v0.9.0：手机直接打开 https://jay1023cn.github.io/mcd-china-map/ ，可记手账、拍照／选相册、看地图、收藏、生成分享卡与备份，不要求本机服务或 Token。Windows 本机完整版作为备选，可接入官方 MCP 查询／同步完成订单并自动整理成手账。手机官方同步仍待用户服务器接入，记录保存在当前浏览器，不自动跨设备同步。正式体验招募仍按用户具体渠道安排；宣传与入口见 [GROWTH.md](GROWTH.md)。

## 体验步骤

主持人先说明是记录体验，不是测试参加者。出现困难时先观察；需要帮助就直接帮助，并记下帮助发生在哪一步，不让对方反复受挫。

| 步骤 | 给体验者的任务 | 观察与记录 |
| --- | --- | --- |
| 1. 打开 | 用手机浏览器打开公开链接 | 能否加载页面；手机系统／浏览器；是否为应用内浏览器；提示与所用版本；是否需要协助 |
| 2. 看一眼 | 先看页面，说说你觉得它能用来做什么 | 用体验者原话记录理解，先不解释定位 |
| 3. 记一餐 | 记下自己熟悉的一家门店，也可自编记录；照片与随手记任选 | 是否找到新增入口；省份、城市、门店是否容易填；保存是否成功；用时和协助情况 |
| 4. 找回来 | 回到地图，找到刚才那条记录，再打开看一眼 | 是否理解省份点亮与城市标记；是否期待精确门店位置；能否找回记录 |
| 5. 保存与备份 | 刷新看看记录是否还在，导出一份备份 | 刷新是否保留；是否知道文件用途；备份只留在体验者本机，不发送给主持人 |
| 6. 再记的理由 | 说说下次什么情况下会再次打开它 | 具体场景与顾虑；口头意愿单独记录，不能当成实际回访 |

导入恢复可以在自愿的独立环节进行：使用专门的空白浏览器上下文和体验者自己的体验备份，确认记录能恢复；不要覆盖日常手账。若没有做，只记“未体验”，不要记为通过。

普通手机体验不要求 MCP。官方门店查询与完成订单自动整理目前用 Windows 本机完整版，邀请具备条件且自愿参加的人另测；使用者自己输入 Token，主持人不读取、不收集原始订单及其关联门店、地址或图片。手机静态页不安排官方同步任务。

## 反馈问题

v0.8.0 可增加自愿任务：在想去清单修改一句理由，生成“分享下一站”卡，看看照片、理由与门店展示是否符合选择，并复制或保存。询问“朋友看到后，会理解这是计划还是已经去过？”与“刚改的理由有没有出现在卡片上？”。只记录实际完成的操作，不把计划卡当作到访，也不把复制计为已发送。目前尚未执行此外部体验任务。

先问实际发生的事，再问期待；可以按过程选问，不强迫每位体验者回答整套问卷。

1. 刚打开时，你觉得这个页面可以用来做什么？
2. 记录这一餐时，哪一步让你停住了？你当时以为应该怎么做？
3. 哪项信息最难填？如果不记这一项，会不会更愿意保存？
4. 回到地图以后，你是怎么找刚才那条记录的？有没有和预期不同的地方？
5. 这条记录让你想起了什么？和直接翻相册或看订单相比，它对你有没有用，为什么？
6. 下次你会在什么时候再打开它？如果不会，最主要的原因是什么？
7. 如果只能改一个地方，你会选哪里？改完会帮助你完成什么？

可选补问：你觉得照片、餐品、随手记中哪项最想留下？你现在在哪里记这些？不要把“自动导入是不是很方便”“喜欢这个地图吗”作为主要问题。

本机版进阶体验分别询问：门店查询是否帮助少填信息；订单自动生成与编辑／删除是否容易理解；哪些自动补充信息需要纠正。只有亲自体验后才记录这些模块的结果。

## 如何确定优先级

人数不是唯一依据，先看问题是否阻断记录或导致丢失，再看它影响多少实际体验者。

| 优先级 | 判定依据 | 下一步验证 |
| --- | --- | --- |
| P0 | 已有证据显示保存／刷新导致记录丢失，或备份恢复破坏现有记录 | 保留问题版本与复现步骤；使用虚构数据独立复现；验证修复后记录完整，并回访实际受影响者 |
| P1 | 无法启动、无法保存第一条、核心路径必须反复求助 | 定位最早卡住的步骤；验证相同环境下能完成该步骤，再观察首次使用者能否独立完成 |
| P2 | 能完成记录，但找回、理解地图或填写信息有明显负担；有证据支持的新需求 | 明确要减少哪个动作或误解；用针对该路径的体验比较验证，不直接照单增加功能 |
| P3 | 少量外观偏好、使用场景尚不清楚的建议 | 保留原话，确认场景和期望；证据不足先不安排开发 |

P0 仅需可信的单例就应调查；影响人数未知写“未知”。所有建议先写反馈事实，再提出解释与方案；解释是待验证判断，不能伪装成用户要求。

主开发对话可读取此表，将已核实问题转成开发任务。此文档不自行安排发布或向其他对话发送消息。

## 一轮结束后怎么复盘

以下字段目前全部待收集，不填写假设数字：

- 实际邀请、报名、开始体验的人数分别是多少？“已发邀请”不等于“已开始”。
- 开始体验的人中，独立保存第一条、协助后保存、未保存分别多少？附具体版本和最常见卡点。
- 实际体验地图找回、刷新保留、导出与恢复的人数及结果分别是多少？未体验单列。
- 愿意再记录与不愿意的具体理由是什么？后续实际回访另外统计，不用意愿替代。
- 有哪些已核实问题必须先修？有哪些需求证据还不足？是否具备扩大招募的条件？

主持人观察、用户自述、用户转述、产品推断分别标注。每次复盘保留版本与证据编号，下一轮才能判断问题是否真的改善。
